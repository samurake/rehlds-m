# ReHLDS-M

[English](README.md) | Русский

ReHLDS-M 1.4.0 заменяет загрузчик HLDS в Linux и Windows. Форк основан на
[hun1er/rehlds-m](https://github.com/hun1er/rehlds-m). Движок, игровая библиотека,
Metamod и плагины AMXX поставляются отдельно.

[Релизы](https://github.com/samurake/rehlds-m/releases) ·
[Сборки](https://github.com/samurake/rehlds-m/actions/workflows/build-and-test.yml)

## Требования и установка

- Linux: 32-битная glibc 2.34 или новее, `/lib/ld-linux.so.2`, процессор с SSE4.2.
- Windows: Windows 10 / Server 2016 или новее. DLL Visual C++ x86 включены в архив.
- Установленный сервер HLDS/ReHLDS с отдельными библиотеками движка и игры.

В Linux файлы `hlds_linux`, `libstdc++.so.6` и `libgcc_s.so.1` размещаются в
корне сервера, рядом с `hlds_run` и каталогом игры. Сохраните право на выполнение
для `hlds_linux`. Проверка архива, резервное копирование и откат описаны в
[инструкции установки](tools/release/INSTALL-linux.md).

В Windows остановите сервер, сохраните старый загрузчик и DLL среды выполнения,
затем скопируйте `hlds.exe` вместе со всеми CRT DLL из архива в корень сервера.

## Настройка

Файл `rehldsm.cfg` располагается рядом с исполняемым файлом. Не перезаписывайте
существующую пользовательскую конфигурацию без проверки. Все параметры читаются
только при запуске процесса; смена карты их не перезагружает.

[Образец](data/rehldsm.cfg) задаёт 1500 итераций/с, отчёты каждые 60 секунд и
асинхронный вывод. Предел — 2000 итераций/с. Для целевого режима оставьте
`sys_ticrate 0` и `fps_max 0` в игровом `server.cfg`.

Удалите старый параметр запуска `-targetfps`: целевая частота теперь задаётся
только в cfg. При `target_fps = 0` используются уровни `-pingboost` 0–5,
с тем же пределом 2000. Частота кадров движка зависит от нагрузки и может быть ниже.

[Справочник конфигурации](docs/startup-configuration.md) описывает допустимые
значения, приоритеты, метрики и ограничения вывода.

| Параметр `rehldsm.cfg` | Допустимые значения | Без параметра | В образце |
| --- | --- | --- | --- |
| `target_fps` | 0–2000 итераций/с | 0 | 1500 |
| `frame_stats_seconds` | 0–3600 секунд | 0 | 60 |
| `async_output` | `true` / `false` | false | true |
| `output_queue_capacity` | 64–4096 сообщений | 1024 | 1024 |
| `output_flush_ms` | 10–1000 мс | 100 | 100 |

Профиль с целевой частотой 2000 из нагрузочных тестов:

```ini
target_fps = 2000
frame_stats_seconds = 60
async_output = true
output_queue_capacity = 1024
output_flush_ms = 100
```

Недопустимые/повторные параметры останавливают запуск. Асинхронный вывод
ограничен по памяти и может терять сообщения при переполнении; следите за
счётчиками. Инструкции с точными путями:
[Linux](tools/release/INSTALL-linux.md) / [Windows](tools/release/INSTALL-windows.md).

| Команда | Назначение |
| --- | --- |
| `--version` | Версия и ревизия без загрузки движка. |
| `--check-config` | Проверка cfg без запуска сервера. |
| `rehldsm_version` | Версия работающего загрузчика через консоль или RCON. |
| `rehldsm_stats` | Отчёт через ввод загрузчика; не команда RCON. |

Сохранены `-condebug`, `-conclearlog`, `-ignoresigint` и `-pidfile <filename>`.
Консоль поддерживает редактирование, дополнение и историю из 100 команд в
`input_history.txt`. Закрытие stdin не останавливает сервер.

## Измеренная производительность

В раннем сравнении каждый вариант запускался три раза: 8 секунд прогрева,
30 секунд измерения, одна и та же ReHLDS/ZP-среда и запрошенная частота 2000.
Медианы частоты принятых кадров движка:

| Игроков | Классический загрузчик, `sys_ticrate 2000` | RC2, `-targetfps 2000` | Сборка 1.4.0 с `target_fps = 2000` |
| ---: | ---: | ---: | ---: |
| 10 | 869.2 | 1990.9 | 1981.2 |
| 32 | 813.2 | 1904.0 | 1919.9 |

Сборка с cfg дала около 2.28×/2.36× частоты классического загрузчика, но
использовала больше процессорного времени и не всегда превосходила RC2.
Оба целевых режима ReHLDS-M использовали `sys_ticrate 0` и `fps_max 0`.

Отдельная проверка финального исходного кода перед тегом использовала
60 секунд прогрева и 120 секунд измерения: 1990.7 FPS при 10 игроках и
1913.4 при 32. Это не новое парное сравнение со старым загрузчиком.
30-минутная измеряемая проверка при 32 игроках прошла четыре смены карты.
Это локальные тесты со скриптовыми fake clients, не гарантия 2000 FPS или
стабильности хостинга. Полные CPU/задержки, условия и ограничения приведены в
[английском README](README.md#measured-performance),
[измерениях](docs/benchmarks.md) и [проверках](docs/testing.md).

## Сборка

Используйте [Linux builder](tools/linux/README.md) или `tools/windows/build.cmd`.
Матрица проверки: GCC 15, GCC 11, GCC 11 ASan/UBSan и MSVC x86.
Для прямой сборки нужны CMake 3.21+ и компилятор C++20 с поддержкой 32-битного ABI:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DBUILD_UNIT_TESTS=ON
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```

Прямая сборка не выполняет все проверки совместимости релизного архива.
`OPTIMIZE_FOR_CURRENT_CPU=ON` разрешает инструкции процессора машины сборки.
Другой сервер может их не поддерживать. Переносимые релизы оставляют этот параметр
выключенным; оптимизация Release и LTO уже включены. Прирост FPS не гарантируется.
